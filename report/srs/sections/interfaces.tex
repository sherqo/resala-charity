\section{External interfaces and data}

\subsection{User interfaces}

The product offers two interfaces over the same core:

\begin{itemize}
  \item a \textbf{graphical interface} with a dashboard and one screen per module (donations, payments, donors, volunteers, events, beneficiaries, messages, and reference data);
  \item a \textbf{console interface} with a numbered menu, kept as a fallback and as evidence that the business rules do not depend on one presentation layer.
\end{itemize}

Both interfaces use the same terminology and the same confirmation behaviour for destructive actions.

\subsection{Communication interfaces}

Email, SMS, and social media are represented by three interchangeable channels. In this version the channels are simulated: a message is validated, recorded, and displayed instead of being transmitted. The interface is designed so that a real provider can replace the simulation without changing the communication screen or the services that send messages.

The main relationships are: a donor has many donations; a donation has at most one payment; a volunteer has many skills and many hour records; an event has one type and many registrations; a beneficiary has one need type and many distributions; a distribution may be linked to one donation.
